# V2 design — accounts, history, async grading, spoken questions

Date: 2026-08-02
Status: approved, not yet implemented

## What V2 adds

V1 grades one answer inside the HTTP request and forgets it. V2 adds accounts,
persistence, a history page, spoken questions, and moves the slow half of grading out
of the request so results can be emailed instead of waited on.

Five things were asked for: sign-up/login, a database for assessments and profiles, a
page for past assessments, TTS for the questions, and a more efficient audio codec.
Two more were added during design: the judge runs locally in development, and results
are deferred and delivered by email.

## Decisions and why

### The async split falls between ASR and judge

Not around the whole request. ASR is ~3s and needs the audio; the judge is 20–60s and
needs only text. So `/submit` transcribes synchronously and the judge runs later on the
transcript alone.

This is what keeps audio out of storage. The alternative — hand the whole answer to a
worker — forces a blob store, presigned URLs and TTL cleanup, and means candidate audio
is written down somewhere. Here the audio exists in memory for one request and dies with
it. That is a stronger privacy property than V1's, not a weaker one, and it matches the
V1 flow where per-answer capture is already separate from whole-test evaluation.

### Judge: local in dev, cloud in demo, one seam

`evaluate.py` already calls OpenAI-shaped `chat_completion` with `response_format`, and
`InferenceClient` accepts `base_url` + `api_key` (verified). So the backend is a config
change, not a code path:

```python
InferenceClient(base_url=JUDGE_URL, api_key=JUDGE_KEY, timeout=120)
```

| `JUDGE_URL` unset | cloud, `meta-llama/Llama-3.3-70B-Instruct` |
| `http://localhost:11434/v1` | Ollama, `qwen2.5:14b` |
| `https://api.openai.com/v1` | OpenAI, `gpt-5-nano` |

Same prompt, same `_parse()`, no new dependency. Ollama's `format` and OpenAI's
structured outputs both take a full JSON schema, which is stricter than today's
`{"type":"json_object"}`.

**Cost is not the reason for a local judge.** All 50,000 answers cost roughly $18 of
judge tokens and $33 of ASR on published rates; self-hosting is ~$241/month for an
always-on GPU that sits idle, and the crossover is ~500–600K answers/month — 10× beyond
the stated ambition. The surviving reason to run locally is that the judge prompt carries
the candidate's verbatim transcript, and a local judge is the only version where that
text never leaves the machine. Development is where iteration volume is highest, so local
runs there and cloud serves the demo.

### Deferred results, emailed as a link

Nobody waits on a spinner, so a 20–60s judge is fine. The email carries a link, never the
report: mail passes through third-party MTAs and is archived indefinitely by the
recipient's provider, whereas a link keeps the transcript on the server where it can
actually be deleted. `CLAUDE.md` already forbids logging transcripts for this reason —
emailing them would break the same guarantee by a different route.

### TTS is a build step, not a route

The bank is fixed: 21 questions, 1,611 characters. Every candidate hears the same
sentences, so generating per-request pays repeatedly for byte-identical output — and
measured latency was **72.9s to produce 4.5s of audio**. Pre-generating is the only
viable design, not a preference.

`hexgrad/Kokoro-82M` is the sole usable model: `espnet/kan-bayashi_ljspeech_vits` and
`facebook/mms-tts-eng` both return `providers=[]`. There is no voice to choose.

The original request named `pipeline("text-to-speech", ...)`, which is the `transformers`
API and downloads weights locally — forbidden by `CLAUDE.md`. The cloud equivalent is
`_client().text_to_speech(text, model=...)`, same client and token as ASR and the judge.

### SQLite, with Postgres behind one file

`sqlite3` is stdlib, so this adds no runtime dependency, and Railway, Fly.io and Render
all provide persistent volumes that survive deploys. It only fails on genuinely ephemeral
filesystems like Cloud Run. `src/db/store.py` owns every SQL statement, so the swap stays
contained if that day comes.

### A jobs table, not Redis

Once a database exists, a `jobs` table plus a polling worker is the same durability with
no new service and no new dependency. At 2–3 jobs/minute Redis buys nothing.

## Layout

The target tree. Today `questions.json` still lives in `app/`, and `data/`, `src/` do not
exist — slice 1 creates them.

```
app/
  __init__.py      entrypoint: truststore, dotenv, setup_logging, run()
  main.py          FastAPI routes only
  evaluate.py      the grader — prompt, parsing, weighting
  index.html
data/
  questions.json
  audio/<id>.opus  generated once, committed (~405 KB for 21 files)
  practice.db      gitignored via data/*.db*
scripts/           scratch POCs, untracked (scripts/.gitignore is `*`)
src/
  constants/
    constants.py   LEVELS, ASR/JUDGE/TTS model + base_url, gate thresholds,
                   cookie name/TTL, poll interval, token TTL
    filepaths.py   ROOT, LOG_DIR, LOG_FILE, DATA_DIR, AUDIO_DIR, DB_PATH,
                   QUESTIONS_JSON, INDEX_HTML, SCHEMA_SQL
  helpers/
    audio.py       decode, RMS gate, Opus handling
    security.py    scrypt hash/verify, hmac cookie + token sign/verify
    mailer.py      smtplib + EmailMessage
    speech.py      TTS build step (`python -m src.helpers.speech`)
  db/
    schema.sql
    store.py       every SQL statement — the only file that knows SQL
```

**Import direction:** `app.main → app.evaluate → src.*`. Nothing under `src/` imports
FastAPI or knows HTTP exists. This replaces the current `main → evaluate` rule.

**Packaging:** `packages = ["app", "src"]` plus `force-include` for `data/` and
`schema.sql` — neither is a Python package, so a wheel would otherwise ship without the
question bank or the schema.

## Flow

| Step | Endpoint | Does | Latency |
|---|---|---|---|
| 1 | `POST /submit` | decode → RMS gate → ASR → store transcript → `{answer_id, words}` | ~3s |
| 2 | `POST /assessments/{id}/finish` | insert one `jobs` row per answer → "we'll email you" | instant |
| 3 | worker thread | claim job → judge → on the assessment's last job, send one email | 20–60s/answer, nobody waiting |
| 4 | `GET /reports/{token}` | render the existing report UI | — |

## Schema

SQLite, WAL, STRICT.

```
users         id, email UNIQUE, password_hash, created_at
profiles      user_id PK, name, default_level
assessments   id, user_id, topic, level, overall, started_at, finished_at
answers       id, assessment_id, question_id, transcript, scores JSON, seconds
jobs          id, answer_id, status, attempts, claimed_at, error
report_tokens token PK, assessment_id, expires_at
```

Job claiming:

```sql
UPDATE jobs SET status='running'
WHERE id = (SELECT id FROM jobs WHERE status='pending' ORDER BY id LIMIT 1)
RETURNING id
```

SQLite serializes writes, so this is atomic without `SKIP LOCKED` — verified below.

**Ceilings to mark with `ponytail:` comments:** the worker polls, so a job waits up to one
interval; stuck jobs need a watchdog resetting `claimed_at` older than N minutes; retries
are an `attempts` column, not exponential backoff.

## Auth

`hashlib.scrypt` for passwords, `hmac`-signed session cookie
(`HttpOnly; SameSite=Lax; Secure`), `secrets.compare_digest` for comparison. All stdlib.

Frontend stays served by FastAPI from the same origin, which avoids `SameSite=None` and
third-party-cookie blocking entirely. Splitting to a CDN would save nothing on a single
HTML file and cost real cookie complexity.

## Slices

Each leaves one runnable check.

1. **Layout refactor** — `src/`, `data/`, `filepaths.py`. No behaviour change; `demo()`
   must still pass. Own commit, since it touches the logging setup.
2. **Store + auth** — schema, `store.py`, signup/login/logout.
3. **Persist** — split `/submit` to ASR-only, write assessments and answers.
4. **Async + email** — `jobs`, worker, `/reports/{token}`, mailer. Built against a stdlib
   debug SMTP server so it is testable without a Resend account or DNS.
5. **Opus + Groq ASR** — the audio slice.
6. **TTS** — `speech.py` build step, `<audio src="/audio/{id}.opus">`.
7. **A/B harness** — 70B baseline vs `qwen2.5:14b` local vs `gpt-5-nano`, same transcripts.

**New runtime dependencies across all seven slices: zero.**

## Measured evidence

The POCs live in untracked `scripts/`, so these numbers are recorded here because nothing
else keeps them.

**Opus** (`scripts/poc_opus.py`, run twice, reproduced):

```
wav  (baseline)   684 KB   4.2s / 15.7s   71 words   baseline
ogg/opus 16k       73 KB   2.7s /  2.9s   74 words   88.3% match
ogg/opus 48k      164 KB   402 Payment Required
ogg/vorbis 16k    116 KB   402 Payment Required
```

9.4× smaller, faster, more stable. The 88.3% is cosmetic — "A hash map" vs "The HashMap",
"eight" vs "8", "red black" vs "red-black" — and the judge prompt already instructs the
model to ignore punctuation and capitalisation.

**TTS** (`scripts/poc_tts.py`):

```
hexgrad/Kokoro-82M   72.9s api   4.5s audio   226 KB raw -> 19.3 KB opus (24 kHz mono)
```

Round trip back through the app's own Whisper:

```
said : Explain how a hash map works, and what happens when two keys collide.
heard: Explain how a HashMap works and what happens when two keys collide.
```

Word-perfect. The deltas are spelling, not mishearing — the generated speech is verifiably
intelligible. Whole bank projects to ~95s of audio, ~405 KB across 21 files.

**Job claiming**: 4 concurrent workers racing for 100 jobs produced 100 claims, 100
unique, zero double-claims on SQLite 3.50.4.

**Judge cost** at 50,000 answers (37M in / 45M out), published rates captured 2026-08-02:

| judge | cost | with batch −50% |
|---|---|---|
| DeepInfra Llama-3.3-70B | $18.10 | $9.05 |
| OpenAI `gpt-5-nano` | $19.85 | $9.93 |
| OpenAI `gpt-5` | $496.25 | $248.12 |
| Self-hosted A6000 48GB, always on | $240.90/mo | — |

ASR: Groq Whisper V3 Turbo $0.04/audio-hour = $33.32 for 833 hours. Current HF/fal-ai
routing publishes no per-model rate and is what returned 402 during both POCs.

Deferring results unlocks batch pricing (~50% off), which earlier analysis had ruled out
on the assumption grading was synchronous.

## Open risks

**Slice 7 is load-bearing, not ceremony.** 2026 research (SLMJury arXiv:2606.07810;
*Reliability without Validity* arXiv:2606.19544, 541K judgments) found small judges shift
score distributions and flip on 13.6% of repeat runs. `LEVELS` weights are calibrated
against 70B output, and the scores are the product. Grading single answers rather than
pairwise avoids most position bias, but the harness is what says whether a smaller judge
is trustworthy — and it gates ever promoting one past dev. `qwen2.5:14b` throughput on
M4 Pro is unverified (20–40 tok/s inferred, so 22–45s for 900 tokens); `ollama` is not
installed yet.

**Slice 5 has an unsolved gap.** `MediaRecorder` emits WebM/Opus and `libsndfile` cannot
read WebM. Either the browser repackages to Ogg or the server extracts the Opus stream.
To be settled in the slice, not guessed at now.

**Slice 4 needs things outside the repo** — a Resend account (3,000/month free, SMTP on
every tier) and a sending domain with SPF/DKIM/DMARC.

**HF credits are currently depleted** (402 on both ASR and TTS), so slice 6's generation
step and slice 7's baseline both need credits or a different provider before they run.

## Explicitly out of scope

- GitHub Pages hosting — parked by the owner ("keep it in the back burner"), including
  the visitor-supplies-own-token pattern. `HF_TOKEN` must never reach the browser or be
  inlined into a static artefact; GitHub `vars.*` are plaintext and `secrets.*` are masked
  only in logs, not in deployed files.
- Redis, Celery, ARQ, RQ — a `jobs` table covers this volume.
- Object storage for audio — the ASR/judge split removes the need.
- Postgres — `store.py` keeps it one file away.
- Self-hosting Whisper. Ollama cannot serve it at all (llama.cpp backend, text and vision
  only), so a local judge leaves the ASR bill untouched by design.
